What happens inside the Python backend?
The API endpoint is:

POST /api/images/analyze

The backend validates the image, decodes it using OpenCV, retrieves the selected camera's check policy, runs the relevant YOLO models and filters unsupported or unselected classes.

It then draws bounding boxes and returns the detections together with a Base64-encoded annotated JPEG.

The image is stamped with a warning indicating that this is sample analysis, unconfirmed and not recorded as an incident.

Does uploading an image send a notification?
No. The image analysis endpoint explicitly returns:

{
  "source": "UPLOADED_SAMPLE",
  "saved_as_incident": false
}

The full response also includes the selected checks, detections, potential violation count and annotated image data.

That means image testing is separate from the live-camera incident system. It is useful for model demonstration without creating artificial factory incidents.

3. Selecting the correct AI checks for image testing
Your project deliberately uses strict class selection.

This means the system should display only detections relevant to the chosen camera's saved safety checks.

Imagine a YOLO model contains Helmet, Vest, Gloves and Mask classes.

If your camera policy enables only Helmet detection, the image lab should not suddenly report Gloves or Mask violations.

Only loaded and supported models can provide actual predictions.

For example, your face_shield_candidate.pt contains the no_faceshield and no_appron dada classes, but these are still unregistered experimental candidates. The regular AI Test Lab does not automatically treat them as approved live detectors.

To demonstrate those models separately, you can use the already prepared annotated-image outputs from your local YOLO evaluation.

Why is selection important? It makes the AI testing behavior consistent with camera policy. A detection class that is irrelevant to a monitored zone should not appear as a valid safety violation merely because the model knows the label.

How to analyze a recording
Suppose you have a 30-second demonstration video.

Open AI Test Lab → Offline video safety analysis.

By default, the checkbox Use selected camera checks for uploaded video is enabled. This means the video inherits the saved safety-check policy of the currently selected camera.

You can also uncheck it and use an independent video checklist.

The interface provides Copy selected camera checks, Supported only, Select all, Clear all, and Save video checklist controls for users authorized to change policies.

For a clear demo, choose only a small number of supported checks rather than selecting every catalog item.

After saving the selection, choose your recording and click Analyze video & create marked output.

The system uploads the file to the Python server and creates a background processing job within the running application.

The counts represent detections across video frames, not 45 different helmet violations or 180 unique employees.

For example, a single worker appearing without a helmet across 45 frames may account for many of those detections.

This is an important limitation to explain to your examiner. The offline video pipeline is primarily an annotation and inference tool, not a complete employee-identification or event-counting system.

Where is the processed video stored?
The server creates a job directory under:

D:\GEC_SafetyGuard_2026\video_outputs\

It stores job metadata and the annotated MP4. The output can be downloaded by the account that uploaded the video.

Completed analysis history can be reopened after restarting the server, provided the files are still retained.

The project includes retention-cleanup utilities; do not assume test videos should remain stored indefinitely.

How to run this in your actual project
Open AI Test Lab → Simulated sensor experiment as Admin or Safety Officer.

Enter the smoke concentration and temperature values, then click Send synthetic reading.

The backend endpoint is:

POST /api/sensors/simulate

When a threshold is crossed, the system inserts an incident with:

{
  "source": "SIMULATION_SENSOR",
  "severity": "TEST",
  "type": "SMOKE"
}

This example represents one synthetic SMOKE record. A temperature threshold crossing instead uses HIGH_TEMPERATURE.

The UI reports generated incident IDs. You can then find those incidents in the Overview or Incidents page.

Why does synthetic sensor testing create an incident when image/video testing does not?
Because the sensor experiment is explicitly designed to demonstrate the incident-recording workflow.

Image and video testing demonstrate model inference. Synthetic sensor testing demonstrates how sensor readings could be converted into database events.

But the source and TEST severity ensure the records are not mistaken for confirmed factory hazards.

Your separate Sensor Concept page also presents hypothetical examples of future sensor integration. It is informational; actual sensor hardware is not connected.

There is one important security distinction: the image and video upload endpoints currently require authentication but do not explicitly restrict their roles to Admin, Operator and Safety Officer. The Supervisor UI hides the Lab, but a directly constructed authenticated API request may still reach those upload endpoints.

For genuine industrial multi-user deployment, that backend role restriction should be tightened. The UI restriction alone is not a sufficient access-control boundary.

Upload security protections
The code validates uploaded image types, sizes, dimensions and decoding. Video uploads are restricted by extension, size and runtime duration.

Video processing uses generated job identifiers rather than arbitrary client-supplied output paths, and access to completed video jobs is owner-scoped.

However, uploaded worker images and videos can contain sensitive workplace information. Use authorized materials, restrict server access and apply an appropriate retention policy.

11. Common viva questions and answers
Q1. Why is AI Test Lab separate from Live Monitoring?

Because AI Test Lab is for controlled experimentation with uploaded media, while Live Monitoring handles active camera streams and qualifying safety incidents.

Q2. Does uploading an image create an incident?

No. The image endpoint explicitly marks its results as unconfirmed sample analysis.

Q3. Can uploaded videos be downloaded after processing?

Yes. Successful jobs generate an annotated MP4 that the uploading account can download while the retained output exists.

Q4. Is one video frame detection equal to one worker violation?

No. The same object may be detected repeatedly across many frames.

Q5. What happens if a video contains a helmet but no violation?

A compatible positive-class model may show the helmet as present. Failure to detect a helmet does not automatically establish a violation.

Q6. Does the Sensor Lab use physical sensors?

No. It uses manually entered numerical readings and threshold rules.

Q7. Why does the synthetic sensor module create incidents?

To demonstrate how future sensor integration could connect measured conditions to the existing incident database and notification workflow.

Q8. Can I use the 300 ppm smoke threshold in a real factory?

Not as an approved safety threshold. It is an illustrative value in this prototype and has not been established as a validated industrial limit.

Q9. Are Face Shield and Apron fully operational in the Lab?

They have a trained checkpoint with holdout evaluation results, but are not registered as approved live detectors. Separate candidate-model inference can be demonstrated.

Q10. Can AI Test Lab replace field validation?

No. Model performance on selected images or videos does not establish real-world reliability across factory camera positions, lighting, equipment and operating conditions.

12. One-minute viva explanation
"Our SafetyGuard AI includes an AI Test Lab for testing and demonstrating detection capabilities independently of live factory cameras.

In the Image Lab, an authenticated user can upload a JPEG, PNG or WebP photograph. The backend uses OpenCV and configured YOLO models to identify selected classes and return an annotated image with prediction labels and confidence scores.

The Video Lab accepts recorded footage and processes it frame by frame. It creates a new annotated MP4, displays processing progress and allows the user to download the output. Video detection counts represent observations across frames, not unique workers or confirmed incidents.

We have also implemented a simulated sensor experiment. Users can enter hypothetical smoke and temperature readings, which are checked against configured demonstration thresholds. When a threshold is exceeded, the system creates an incident explicitly labeled as TEST.

Image and video tests do not create live safety incidents. This separation lets us evaluate the AI models and demonstrate the incident workflow without presenting experimental observations as confirmed factory emergencies."

13. What makes AI Test Lab valuable?
The Image Lab demonstrates single-frame inference. The Video Lab demonstrates offline frame-by-frame inference and annotated output generation. The Sensor Lab demonstrates threshold-based event creation without physical sensors.

Together, these allow you to explain three different ways a safety-monitoring platform can process input, while keeping the results clearly separated from validated industrial operations.

Remember this distinction for your examiner: AI Test Lab tests the detection technology; Live Monitoring observes active cameras; Incident Management handles qualifying events; Analytics reports the records created by those events.
